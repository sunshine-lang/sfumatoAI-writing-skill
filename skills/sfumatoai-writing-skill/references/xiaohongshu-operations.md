## 1. 正文排版

把正文写成可扫读的信息路径，而不是图片脚本的缩写版：

1. 用 1–2 行承接封面，提出问题或反常识判断；
2. 用 2–4 行解释核心机制或步骤；
3. 用 1–2 行补充边界、风险或核验提醒；
4. 把话题放在最后一段。

使用 3–7 个功能性 Emoji 作为视觉路标。让 Emoji 分别承担开场、步骤、结论或风险提醒；短正文可更少。不要连续堆叠相同 Emoji，不要在每句话前机械添加，也不要用 Emoji 代替 Token、LLM 等关键术语。

用确定性计数工具核对正文长度。统计 Emoji、空格、标点和话题，只排除 `\r` 与 `\n`；不要凭目测判断是否低于 200 字。

## 2. 触发实时检索

在以下场景进行当前小红书平台采样：

- 用户询问热门话题、流量、搜索量或近期趋势；
- 用户要求从小红书运营角度优化；
- 话题包含快速变化的产品、模型、事件或平台词；
- 现有建议主要依赖经验，无法判断当前用户是否仍在使用这些词。

若可用，调用 `xhs-explore` 并完整遵守其 `SKILL.md`。若平台访问、登录或依赖不可用，停止声称“当前热门”，明确把结果标为语义匹配或经验建议。

## 3. 平台采样

先定义三类查询，不要只搜一个泛词：

1. **精准主题：**内容的标准中文名或常用英文缩写；
2. **受众与任务：**主题 + 入门、学习、教程、图解等真实内容意图；
3. **内容形式：**原理、概念、路线、对比、避坑等与本篇结构一致的词。

执行以下最小采样：

- 搜索 2–3 个查询词，记录日期、排序和时间筛选；
- 比较综合结果与收藏导向结果，不把最高点赞自动视为最相关；
- 从结果中选择 2–3 篇与当前内容最接近的笔记，读取详情中的实际话题；
- 记录标题、点赞、收藏、评论、分享和实际话题；缺失字段保持缺失，不自行补值；
- 优先分析内容匹配度和收藏/点赞关系，不把单篇爆款外推为平台规律。

完成 3 篇详情后停止批量读取；需要扩大样本时，按 `xhs-explore` 的防风控要求等待并分组。

## 4. 话题分层

从下列层级组成推荐集合：

| 层级 | 默认数量 | 作用 |
|---|---:|---|
| 精准主题词 | 1–2 | 说明这篇内容究竟讲什么 |
| 学习意图词 | 1–2 | 承接主动搜索、学习和收藏需求 |
| 内容形式或受众词 | 1 | 标记科普、图解、入门或目标人群 |
| 泛领域词 | 0–1 | 补充更大的内容分类入口 |
| 实验词 | 0–1 | 用于 A/B 替换，不与推荐组同时堆叠 |

通常提供 5–7 个话题；内容范围很窄时可以更少。逐个检查：

- 话题是否在标题、正文或图片中得到实际支持；
- 是否与另一个话题只是大小写、简称或同义重复；
- 是否会引入产品、职业、面试、Agent 等正文未覆盖的流量；
- 是否挤占了事实边界和核心解释的字符预算。

优先替换冗余话题，不在原有话题后无限追加。若加入话题后超过 200 字，先压缩重复表述，保留定义和风险提醒。

## 5. 证据边界

把结论分成三类：

- **平台观察：**在指定日期、查询和样本中实际看到的标题、指标和话题；
- **运营推断：**根据内容匹配度、搜索意图和互动结构提出的建议；
- **不可证明的因果：**某个话题导致流量上涨。不要把它写成事实。

说明样本数量和局限。不要承诺“加上就会爆”“必然提高流量”。把话题视为分类与搜索辅助，同时提醒封面点击、标题表达、首屏价值和收藏动机也会影响表现。

## 6. 输出格式

按以下顺序交付：

1. 推荐话题组合，可直接复制；
2. 每个话题的层级与作用；
3. 一组 A/B 替换项及适用条件；
4. 不建议使用的话题及不匹配原因；
5. 替换后的正文字符数；
6. 平台采样日期、范围和“相关性不等于因果”的限制。

用户只要求分析时保持只读；只有用户明确要求更新文案或交付文件时才写入文件。
